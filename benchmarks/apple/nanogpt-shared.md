# Shared SQL execution with CPU and MLX kernels

This comparison combines shared common table expression (CTE) execution
with [EinFold](https://github.com/xqlsystems/einfold), a tensor optimizer for
SQL, and [MLX](https://github.com/ml-explore/mlx), Apple's array framework.
[ddx](https://github.com/xqlsystems/ddx) still differentiates the original
SQL model. The implementation follows SQL → DataFusion → EinFold → MLX,
including numerical operators generated by SQL differentiation.

The measured machine is an Apple M5 Ultra with 30 CPU cores, 64 GPU cores
and 256 GiB memory. These final `nanogpt-shared-v3-*` runs took place after
game contention ended, one host per process and one benchmark at a time.
No builds or correctness suites ran concurrently with these timings.
Versions: Python 3.12.14, DataFusion Python 55.0.0, ddxdb 0.4.6, MLX 0.32.4
and the local EinFold 0.2.0+xqlmlx.3 patch, with native DataFusion 55.2.0.
CPU partition count is 30.

## Execution changes

- Materialize reused, reachable forward CTEs once. Preserve the attention
  score/softmax/value region so EinFold can fuse it across batch/head keys.
- Retain forward physical plans and prepared ddx programs across training
  steps. Reset execution state through EinFold's reference codec, including
  DataFusion 55's FFI child-replacement path. Disable four dynamic-filter
  settings on the explicit shared executor so cached bounds cannot become
  stale after writes.
- Reuse owned Arrow value buffers. Share immutable integer/string keys
  using exact equality checks and a bounded cache. Retain verified canonical
  ordering so downstream operators need fewer sorts. Changed domains,
  schemas and row counts invalidate affected physical plans.
- Keep join-only ddx stages as logical views until their consumers reduce
  them. Large backward joins otherwise materialize billions of rows before
  performing a matrix contraction. Very large cotangent sums execute their
  reduced branches sequentially. Those compound stages rebind transient
  ddx providers each call; ordinary stages retain physical plans.
- Dispatch validated dense arithmetic through float64 CPU matrix products
  or explicitly permitted float32 MLX matrix/attention kernels. EinFold
  retains SQL key, NULL, duplicate-row and output-domain reconstruction.

The [bridge documentation](../../accelerators/einfold_mlx/README.md)
describes installation and the public experimental `SharedExecutor` API.
Stage boundaries still exchange Arrow buffers. This is not a GPU-resident
training graph, and MLX does not supply the derivatives.

## Timing and correctness method

Every completed training run uses **`--steps 5`** and checks the loss and
every updated parameter against the same JAX float64 reference after every
step. Each host starts from identical seeds and batches. CPU checks use
`rtol=atol=1e-9`; GPU checks explicitly permit float32 arithmetic with
`rtol=atol=3e-5`. `MLX_ENABLE_TF32=0` is set before importing MLX. Every GPU
callback synchronizes before returning Arrow data.

`cpu_forced` and `gpu_forced` retain parameters and prepared queries but
expand the forward CTEs normally. `shared_cpu` and `shared_gpu` add shared
execution. Both pairs set the kernel thresholds to zero to compare actual
CPU/GPU dispatch rather than an automatic policy that can stay on CPU.
Shared hosts use a 4 GiB per-backend working estimate and 4 GiB coordinate
cache budget; library defaults are 512 MiB and 256 MiB respectively. The
plain DataFusion/DuckDB controls also use the checkout's registration fixes.
Each ratio includes the planning, storage and dispatch changes between
the compared final implementations.

Warm time is the mean paired loss + training API time for steps 1–4;
step 0 is excluded. Each of those four steps uses a different batch. These
are single measurements per step, not a statistical confidence interval.
The measured five-step total includes all five loss/training API calls and
cumulative Dataset loading and model-view setup. It excludes JAX reference
work, parameter validation, result-to-Dataset conversion and reporting.
Runner wall time includes those costs and process startup. Forward-only
results time five checked losses and perform no backward pass or updates.

Sampled peak RSS is measured once per second. It is not a hard allocator
limit or a measurement of all Metal driver memory. The runner terminates
only its own child process group when a configured memory/time bound is
crossed. Failed or incomplete runs contribute no training speedup.

Sharing improves the tiny warm CPU step **314 → 206 ms (1.53×)** and GPU
step **371 → 224 ms (1.66×)** against the corresponding unshared prepared
kernel hosts. Shared CPU is **6.12×** faster than plain DataFusion and
**1.48×** faster than DuckDB for that complete warm step. Its five-step
measured total, including preparation/loading, is 1.37 s versus 6.80 s for
DataFusion. These controls all use the final checkout.

At 213K parameters, sharing improves the CPU step **551 → 431 ms (1.28×)**
and GPU step **601 → 482 ms (1.25×)**. At 10.7M parameters, shared CPU/GPU
take **29.26/29.94 s**. GPU remains slower than CPU on these configurations.
The tiny shared GPU host completes **160 matrix and 5 attention kernels**,
versus **1,015 matrix and 200 attention kernels** without shared CTEs.
The 10.7M GPU run completes **410 matrix and 30 attention kernels**. The
improvement from sharing comes from avoiding repeated SQL work and GPU
dispatches.

The 123.6M-parameter, context-16 model completes all five training steps on
both hosts: **164.03 s CPU versus 163.65 s GPU** per warm combined step,
effectively equal in this run. First training queries take 171.98/173.35 s.
Each host takes about 830 s for the measured five-step total and 846 s wall
time. CPU/GPU sampled peak RSS is 38.7/40.0 GiB. The GPU executes 710 matrix
and 60 attention kernels across the run.

At the full context of 1024, the 124.3M-parameter model passes five forward
checks on each host: **6.57 s CPU versus 6.86 s GPU** per warm loss. The GPU
completes 365 matrix and 60 attention kernels. These are forward-only
results; full-context training performance remains unestablished. Across
all 16 final runs, **all 150 loss/update checkpoint records pass**.

## What profiling explains

The original tiny forward loss expands to **9,882 DataFusion physical
operators**, including 2,988 joins and 1,050 aggregates. DuckDB retains nine
shared CTEs and uses 126 operators. A separate CPU timing breakdown found
about 0.94–0.96 s in DataFusion physical planning, 0.013 s in SQL/DataFrame
construction and 0.16–0.21 s executing an existing forward plan. DuckDB's
forward execution including physical planning took 0.024–0.030 s. See the
[raw planning breakdown](nanogpt-plan-breakdown.json). Operator counts are
not comparable for the opaque EinFold FFI nodes, so accelerated hosts leave
that field empty and record completed kernel/stage counters instead.

For the checked five-step 10.7M CPU run, shared-executor counters record
19.4 s planning, 23.4 s stage sorting/storage and 100.9 s execution. These
cover the loss and backward stages together; execution includes native CPU
work and buffer conversion as well as numerical kernels. The GPU run
records 20.1 s, 24.0 s and 103.4 s respectively. GPU dispatch changes the
arithmetic inside a stage, while those surrounding costs remain. The
coordinate cache avoids 5.30 GB of additional key copies and retains
263 MB of immutable keys at the end of that CPU run.

Shared execution addresses the repeated work that made DuckDB faster on
the tiny forward pass. GPU arithmetic alone cannot remove SQL planning,
Arrow coordinate processing, stage storage or many small dispatches. The
[earlier CPU profile](cpu-profile.txt) and [overhead/thread sweep](README.md#training-overheads-and-cpu-parallelism)
also motivated prepared gradients, direct registration and arithmetic
chunk counts. Increasing the partition count above the existing 30-core
default did not consistently improve EinFold, so this comparison uses 30.

A separate five-step 213K GPU [CPU profile](shared-profile.txt), collected
after all timing runs, records 0.81 s in DataFusion execution entry calls,
0.94 s in record-stream iteration, 0.70 s in physical planning and 0.15 s
in the MLX callback. These cumulative costs include nested native work;
they cannot be added as independent phases. JAX reference compilation also
appears in this whole-process profile and is excluded from the benchmark
API timings. The [profile log](shared-profile-demo.log) and
[checked rows](shared-profile-demo.csv) are kept separately from the final
performance table.

An additional contraction-input staging experiment did not resolve the
full-vocabulary backward memory limit and increased the 10.7M model's
first CPU training query from approximately 25 s to 63 s. It was removed.
Sequential reduction staging is reserved for at least 32 UNION branches;
applying it to smaller backward programs also added unnecessary work.

## Precision and size limits

GPU float32 preserves the SQL and ddx formulas, with explicitly different
rounding from float64. It does not provide arbitrary float64 equivalence.
An AdamW test at 213,504 parameters, batch 12, failed the unchanged GPU
tolerance: `wpe.w[48,53]` differed by 4.1264e-5. The float64 reference
gradient there was 1.54198e-8 and the GPU gradient was 1.30217e-8. AdamW's
division by small gradient moments amplified that difference. Applying
AdamW to identical gradients agreed within 3.0e-14 on CPU and 1.7e-14 on
GPU, isolating the discrepancy to numerical gradient precision. See the
[diagnostic](nanogpt-adamw-diagnostic.json) and
[failed checked run](nanogpt-adamw-failed-demo.log). The final comparisons
use SGD; no tolerance was relaxed to make AdamW pass.

The GPT-2 preset follows [nanoGPT's GPT-2 dimensions](https://github.com/karpathy/nanoGPT/blob/master/model.py):
12 layers, 12 heads, 768 channels, context 1024 and vocabulary 50257.
This SQL demo omits biases and dropout and uses tied token/output weights.
The 124,337,664-parameter count includes positional embeddings. Character
inputs from Tiny Shakespeare are padded to the larger vocabulary; these
runs do not use GPT-2 BPE, pretrained weights or GPT-2 quality evaluations.
The six-layer configuration follows
[nanoGPT's Shakespeare character model](https://github.com/karpathy/nanoGPT/blob/master/config/train_shakespeare_char.py)
dimensions, with batch 1 and no dropout here.

The 123,649,536-parameter, context-128 forward loss passed, but backward
execution crossed the 96 GiB sampled-RSS limit. Its ~2.2 s forward timing
does not establish training performance. Successive development attempts
and their exact commands remain in `nanogpt-final-gpt2-128*-runs.json`.
The remaining expensive path includes reconstruction of normalized residual
operands and the tied vocabulary-weight gradient. More GPU arithmetic
dispatch cannot by itself eliminate those relational intermediates.
Reducing context to 16 lets the same 12-layer, full-vocabulary parameter
model complete five checked training updates within approximately 40 GiB
sampled RSS. This establishes short-context training correctness and cost,
while the full context of 1024 is checked only for forward execution.

## Validation and reproduction

The final local suite passed **637 tests**, with 277 skipped and 102
integration tests deselected. Coverage includes SQL bags and NULLs,
coordinate/schema invalidation, repeated changed parameters, snapshots,
batched/head-separated attention, grad/VJP/JVP and typed ddx refusals.
[Python test log](shared-correctness.log). EinFold's native kernel and
planner suites passed 60 tests; four remain ignored upstream, and the
unchanged plain-DataFusion ARM NaN-sign assumption is excluded. See
[kernel tests](shared-native-kernel-tests.log) and
[planner tests](shared-native-planner-tests.log). Ruff checks pass; focused
mypy checks with missing third-party stubs ignored also pass. The native
patch applies cleanly to its pinned revision.

```sh
MLX_ENABLE_TF32=0 PYTHONPATH="$PWD" .venv/bin/python benchmarks/apple/run_nanogpt_sizes.py \
  --preset tiny --steps 5 --batch 4 --learning-rate 0.5 \
  --hosts datafusion duckdb cpu_forced gpu_forced shared_cpu shared_gpu \
  --prefix local-tiny

MLX_ENABLE_TF32=0 PYTHONPATH="$PWD" .venv/bin/python benchmarks/apple/run_nanogpt_sizes.py \
  --preset shakespeare --steps 5 --batch 1 --learning-rate 0.01 \
  --hosts shared_cpu shared_gpu --prefix local-shakespeare

MLX_ENABLE_TF32=0 PYTHONPATH="$PWD" .venv/bin/python benchmarks/apple/run_nanogpt_sizes.py \
  --preset gpt2 --steps 5 --batch 1 --forward-only \
  --hosts shared_cpu shared_gpu --prefix local-gpt2-forward
```

The checked CSVs, complete logs, status records and exact commands use the
`nanogpt-shared-v3-` prefix alongside this report. The summary retains failed
statuses separately and includes source hashes to identify the measured
uncommitted implementation.

The subsequent [native framework comparison](nanogpt-frameworks.md) runs
the same model directly through JAX and upstream nanoGPT's PyTorch model.
It measures the substantial remaining gap to native array training.
