# SQL Shakespeare training matching nanoGPT

This report records the earlier Arrow-output implementation. The later
GPU-resident implementation measures 101.3 ms per warm step over 100
updates (19.98× faster), with a separate fully checked five-step run.
See [the complete performance report](../../NANOGPT_PERFORMANCE.md) and
[resident measurements](resident-summary.json) for its timing scope and
the updated native PyTorch comparison.

[nanoGPT](https://github.com/karpathy/nanoGPT) is a small implementation
of GPT training in PyTorch. The new
[`03_shakespeare.py`](../ml/03_shakespeare.py) trains its Shakespeare
character model through SQL, with gradients generated by
[ddx](https://github.com/xqlsystems/ddx), compact array programs from
[EinFold](https://github.com/xqlsystems/einfold), and optional
[MLX](https://github.com/ml-explore/mlx) GPU execution. It initializes once
per run, then keeps updating the parameters; these are training timings.

The recipe matches the local nanoGPT command: batch 12, context 256,
6 layers, 6 heads, 384 channels, gradient accumulation 1, max iteration
2000, cosine decay through iteration 2000, warmup 100, evaluation every
200 iterations and 20 batches per train/validation split. It also matches
inherited settings: exact GELU, dropout 0.2 at all four types of dropout
site, tied embeddings, no biases, global gradient clipping at 1, and
AdamW with betas 0.9/0.99, epsilon 1e-8, learning rate 1e-3 to 1e-4 and
weight decay 0.1 excluding layer norm gains. The vocabulary has 65
characters and the model has **10,745,088 total parameters**. It is not a
123M-parameter GPT-2 vocabulary model.

## Measured results

Measured November 1, 2026, on Apple M5 Ultra, 30 CPU cores, 64 GPU cores
and 256 GiB unified memory. Both backends completed exactly **five
updates**, using `--steps 5` without shortening the learning-rate schedule.
Each also evaluated 20 train and 20 validation batches at iteration 0.
Runs were serial. PyTorch reference checks were outside each timer.

| Backend | Arithmetic | Computed cache limit | First step | Mean steps 2–5 | Tokens/s, warm |
|---|---|---:|---:|---:|---:|
| Compact CPU | float64 | 32 GiB | 10.362 s | **9.747 s** | 315 |
| Compact MLX GPU | float32 | 16 GiB | 2.523 s | **2.024 s** | 1,518 |

The GPU path was **4.82× faster** than the measured CPU configuration.
The precision and cache budgets differ as shown. This compares these
SQL execution configurations, not native PyTorch or DuckDB performance.
First-step measurements include plan/JIT preparation in the final
process; driver/kernel caches may already have been warmed by earlier
trials. Five steps do not establish model convergence.

Training time includes a loss forward call, ddx backward gradients,
global clipping, all SQL AdamW updates, Arrow conversion and registration
of the new weights/moments. Batch and dropout-mask sampling, evaluation,
reference checks and checkpoint I/O are outside the timer. There are
3,072 training tokens per update. These timings therefore retain SQL's
public Arrow boundaries and the separate loss-forward call.

Every evaluation/training loss, every raw parameter gradient, every
updated weight and both AdamW moments were checked against the original
nanoGPT `model.py` plus PyTorch AdamW after every update. The oracle uses
identical initial arrays, batches and dropout masks, exact GELU and
explicit causal attention. CPU checks use 1e-8 absolute/relative tolerance;
GPU checks use the existing 3e-5 tolerance. Stock nanoGPT samples with
PyTorch RNGs; the SQL script uses NumPy RNGs, so an integer seed alone
does not produce identical independent runs.

Both final runs used strict compact execution with no SQL fallback. The
GPU's peak computed cache was approximately 9.80 GiB. The CPU reached its
32 GiB computed-cache limit and evicted intermediates 3,802 times. These
cache counters are not total process memory. A diagnostic CPU trial with
a 16 GiB cache evicted more often and was slower; it is excluded from the
final comparison because it used a newer ddx source snapshot.

### Native PyTorch MPS comparison

The original nanoGPT `train.py` was also measured with the same model,
batch, context, data split, dropout, exact GELU, clipping, AdamW and
learning-rate schedule, using PyTorch 2.15.0 on MPS, float32 and
`compile=False`. It completed five actual updates; the warm mean again
uses updates 2–5:

| Training implementation | Warm time/update | Tokens/s | Relative to native MPS |
|---|---:|---:|---:|
| Native nanoGPT / PyTorch MPS | **29.35 ms** | **104,652** | 1× |
| SQL / MLX GPU | 2,024.15 ms | 1,518 | **68.96× slower** |
| SQL / float64 CPU, 32 GiB cache | 9,746.51 ms | 315 | 332.03× slower |

The [native results](shakespeare-torch-mps.json) include every synchronized
duration, source hashes, package version and exact configuration.
[`compare_shakespeare_mps.py`](compare_shakespeare_mps.py) executes the
original local trainer with timing instrumentation; it does not modify
the nanoGPT source files. It synchronizes MPS immediately before the
forward/backward/update interval and after gradient clearing. Timing
includes native next-batch prefetch. Evaluation, initialization, logging
and checkpoint I/O are outside that interval.

This is a comparison of the practical training paths. Native PyTorch
keeps weights and optimizer state resident on MPS and performs one
training forward/backward pass. SQL returns Arrow parameter/moment tables
and computes its reported loss in a separate forward call. Consequently
the paths have different execution and output overhead. Matching recipe
settings does not remove those differences. Native RNGs also produce
different initial weights and dropout masks from the independent SQL
run. These measurements are five-step samples, not long-run averages.

The native loop stops when `iter_num > max_iters`; setting `max_iters=4`
therefore runs exactly five updates. `lr_decay_iters=2000` and
`warmup_iters=100` remain unchanged. To repeat the instrumented comparison
in an environment with PyTorch installed:

```sh
PYTHONPATH="$PWD:$PWD/.venv/lib/python3.12/site-packages" \
  /private/tmp/xql-framework-venv/bin/python benchmarks/apple/compare_shakespeare_mps.py \
  --nanogpt-source /Users/cromwellian/nanoGPT --steps 5 \
  --output benchmarks/apple/shakespeare-torch-mps.json
```

## Changes needed for this recipe

- Dropout masks are exogenous SQL tables, freshly sampled for each
  training update and absent from the evaluation graph. ddx differentiates
  the actual masked SQL model.
- An optional [ddx math patch](../../accelerators/ddx_math/README.md) adds
  erf's analytic scalar derivative and preserves erf in derivative plans.
  `xarray_sql.math.register_erf` supplies its SQL implementation and
  equivalent array primitive. This enables nanoGPT's exact GELU.
- Softmax and cross-entropy stabilization use `GROUP BY` and joins.
  Profiling an earlier window-based trial showed repeated traversal of
  shared subqueries during ddx window lowering. The stabilizing maximum
  is held constant: the shared shift cancels from softmax and cross
  entropy, including their parameter gradients.
- Conditional products retain their factors through aliases and
  zero-valued CASE branches. This avoids expanding an attention backward
  temporary of shape 256 × 256 × 12 × 6 × 64, which exceeded the existing
  conservative 1 GiB array guard. The guard remains unchanged.
- AdamW moments occupy separate tables from differentiated weights;
  clipping is computed once in SQL, and prepared update programs are
  reused across iterations.
- Safe NPZ checkpoints contain weights, moments, next iteration, RNG
  states, vocabulary and recipe settings. A correctness test checks that
  resuming produces exactly the uninterrupted SQL trajectory.

The optional builds are `ddxdb==0.4.6+xqlmath.2` and
`einfold==0.2.0+xqlmlx.5`. The ddx patch is based on the exact 0.4.6 release
commit `af71683f6678bb093e600f948c212490a4d8b74b`, excluding newer upstream
changes. The nanoGPT reference is commit
`3adf61e154c3fe3fca428ad6bc3818b27a3b8291`. Other dependencies, commands,
per-step records, counters and source hashes are recorded in
[`shakespeare-summary.json`](shakespeare-summary.json). Intermediate
`shakespeare-matched-*` logs retain failed/superseded trials; only the
`release-*-stable` runs describe the final comparison.

## Run the training script

Use the existing checkout environment after the optional builders have
been installed. From the xarray-sql directory:

```sh
MLX_ENABLE_TF32=0 PYTHONPATH="$PWD" .venv/bin/python benchmarks/ml/03_shakespeare.py \
  --backend dense_gpu \
  --data-dir /Users/cromwellian/nanoGPT/data/shakespeare_char \
  --out-dir out-shakespeare-sql
```

Defaults match the recipe above. As in native `train.py`, `max_iters=2000`
includes iterations 0–2000, or 2001 updates. Add `--steps 5` for an exact
five-update smoke run. Use `--backend dense_cpu --cache-gib 32` for the
measured CPU configuration. For optional independent checks, add
`--verify-nanogpt /Users/cromwellian/nanoGPT` in an environment with
PyTorch installed. See the [training documentation](../ml/README.md) for
resume instructions and timing scope.

The final verified five-step checkpoints are:

- [`GPU last.npz`](shakespeare-matched-release-gpu-stable/last.npz)
- [`CPU last.npz`](shakespeare-matched-release-cpu-stable/last.npz)

Checkpoint binaries are ignored by git; text metrics and logs are retained.

## Validation

The full local suite passed with GPU checks enabled:

```sh
MLX_ENABLE_TF32=0 PYTHONPATH="$PWD" .venv/bin/pytest -q -m 'not integration'
# 704 passed, 277 skipped, 102 network/integration tests deselected
```

The [test log](shakespeare-correctness.log) records the result and existing
warnings. New checks cover erf values/NULLs, UDF replacement, exact GELU
gradients in SQL/CPU/GPU, bounded conditional contractions, and complete
SQL training checkpoint/resume. ddx-core's scalar-rule suite also passed,
including the new erf chain-rule and second-derivative check. Ruff and
`git diff --check` passed.
